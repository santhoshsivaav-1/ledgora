# Product audit, competitor analysis and implementation plan — November 2026

Audited 16 Nov 2026 against the app running at `http://localhost:5173` (API on `:4000`), commit `b101b30`. Written so a developer
can start work from it: every finding says where it is, why it matters and what to change.

## 0. How this audit was done, and what it does not cover

| Done | How |
|---|---|
| **Every screen opened in a real browser** | A fresh account was signed up, given a little data (3 parties, 3 items, 3 invoices, a purchase, an expense) and **105 desktop views and 75 mobile views** (390 px) were visited: every route in `app/router.tsx`, every Settings tab, every Cash & Bank, Accounting and GST Returns page, and 30 report pages. Each visit recorded console errors, failed requests, horizontal overflow, clipped text, unlabelled controls, tiny click targets and "undefined / NaN / null" text. About 125 full-page screenshots were taken and about 20 were reviewed by eye. |
| **The slowness you reported was measured** | The API calls of single navigations were counted and timed (section 3). |
| **The code was scanned** | Hardcoded data, `TODO` / placeholder markers, dead handlers, `console.log`, `localhost` literals, file sizes, test counts, the settings registry (111 keys checked for a reader), the data layer, the auth gate, the notification and search code. |
| **Competitors were researched** | Web search (sources at the end) plus the project's own `COMPETITOR_GAPS.md`. |

**What this audit does not prove — read this before trusting a "clean" line:**

1. **Your login did not work locally** (`forquesolutions@gmail.com` → "That e-mail and password do not match"): that account lives on the Railway deployment, not in the local database. So the audit ran on a fresh local account. **Nothing was tested on Railway**, so the Railway-specific slowness (4–9 s `/profile` calls) is explained from the measured request pattern, not reproduced.
2. **"Loads without errors" is not "works".** The crawl visits screens; it did not click every button, save every form or complete every flow (e-way bill, e-invoice, reconciliation, restore, Google Drive, WhatsApp, payments). Those need a second pass with scripted flows (section 9, Phase 5). The existing browser tests cover sign-up, ITR-3, ITR-4, filing packs (49 checks).
3. **"Each and every line of every file" was not read.** The code base is 52,841 lines in the web app alone. I read the files that decide behaviour and performance (shell, auth gate, data layer, notifications, settings registry, plans, store, the new modules) and measured the rest. Where a module below says *crawl only*, that is all it received.
4. Competitor claims come from vendor pages and comparison sites. Prices disagree between sources, so they are marked as unverified.

## 1. Executive summary

**The product is much more complete than it looks from outside:** 111 settings all wired to a reader (one, `acct.valuation`, has none), 30+ reports, a double-entry ledger, GSTR-1/3B/9/9C/4, CMP-08, IMS, ITR-3 and ITR-4 built from the books and checked against the department's own rules, a CA workflow, an edit log, Hindi and Tamil. **No screen crashed, no screen showed "undefined / NaN / null", and none of the 75 mobile views scrolled sideways.**

**Why it feels slow (section 3, measured):** a single page load makes **36–44 API calls**. The shell downloads the **entire** bills, clients and products collections on every start (for the Ctrl+K search, then keeps only the first 100 / 200 of them) and again for the notification bell; `listBusinesses()` runs seven times per load; sign-in is a three-step waterfall. On a fast local machine this costs about 4 s to settle; on Railway, where each call took 4–9 s, it is the slowness you see.

**Top 12 things to do, in order:**

| # | What | Why | Section |
|---|---|---|---|
| 1 | Stop loading whole collections on start; add one `bootstrap` call; cache `businesses` | Navigation and login speed | 3 |
| 2 | Paginate and index the generic `documents` store | Gets slower with every invoice; unusable at a few thousand | 3 |
| 3 | Fix the squashed "Trial · 7 days left" pill (on every screen) | Visible on all 105 views | 4 |
| 4 | Real `/pricing`, `/privacy`, `/terms`, `/forgot-password` pages | Today all four show the login screen; no public page to sell from, and a legal gap | 5 |
| 5 | Turn payments on (the provider code exists) | "Online payment is not switched on yet": nobody can pay for Silver or Gold | 5 |
| 6 | Direct e-invoice (IRP) and GSTN upload | The biggest gap against Zoho, Tally, ClearTax and Vyapar's higher plans | 7 |
| 7 | Table overflow, header and Settings layout fixes | Clipped Actions column, wrapped badges, clipped inputs | 4 |
| 8 | Accessibility pass (labels, 24 px targets, skip link) | 25+ screens have placeholder-only fields | 4 |
| 9 | Turn the ledger and Cash & Bank on by default for new businesses | Today two gate screens stand between a new user and bank accounts | 6 |
| 10 | Replace the hardcoded default terms and the 200-code HSN list | "No hardcoded data" | 8 |
| 11 | Bank feeds, WhatsApp API and payment links | The collection loop competitors sell on | 7 |
| 12 | Break up the 3,452-line invoice editor and the 1,825-line settings view | Every change is slow and risky | 6 |

## 3. Why navigation, login and onboarding are slow — measured

### 3.1 The evidence

Single navigations on a fresh account, counted by `apps/web/scripts/audit-netprof.mjs`:

| Page | API calls | Worst repeats | Settled after |
|---|---|---|---|
| `/` Home | **44** | `/v1/businesses` ×7, `collections/bills` ×6, `collections/products` ×6, `stockAlertSettings` ×4 | 4.5 s |
| `/reports` | **43** | `/v1/businesses` ×7, `collections/bills` ×4, `collections/products` ×4, `/v1/me` ×2, `/v1/onboarding` ×2 | 4.0 s |
| `/accounting/trial-balance` | **36** | same shell calls, though the page needs none of them | 3.7 s |
| `/parties` | ~38 | same | 3.9 s |

Everything outside the page's own data is shell traffic. Locally each call is a few milliseconds and the page paints in about **200 ms** (measured on all 105 screens: median 201 ms, worst 263 ms), but nothing settles for ~4 s. On Railway each call took 4–9 s (your network tab), and a browser allows about 6 connections per host, so 40 calls queue and every page change waits behind them. That is the slowness.

(Some doubling is React `StrictMode` in development. Real repeats are in the shell, below.)

### 3.2 The causes, in the code

| # | Cause | Where | Effect |
|---|---|---|---|
| C1 | The app shell downloads **all** bills, clients and products on every mount (and again each time the palette opens) to build the Ctrl+K search, then keeps `bills.slice(0, 100)`, `clients.slice(0, 200)`, `products.slice(0, 200)` | `App.jsx:225-240` | Whole tables over the wire to keep 100 rows; grows with the business |
| C2 | The notification bell downloads **all** bills and **all** products and computes overdue, due-soon and low-stock in the browser | `app/useNotifications.js:105-107` | Same data a second time, on every page |
| C3 | `listBusinesses()` has no cache and is called from **~18 places** | `lib/data/accounting.js:9` and 18 call sites (every Cash & Bank, Accounting, GST, ITR, Reports, POS, Settings page) | 7 identical calls per load |
| C4 | `lib/data/*` bypasses TanStack Query (installed, `staleTime` 30 s) | `lib/data/*.js` use `apiFetch` directly | No shared cache, no de-duplication, no background refresh |
| C5 | The generic `documents` store returns **whole collections**, sorted in JavaScript, with no limit, offset or index on document fields | `apps/api/src/modules/workspace/store.ts` (`listDocs`, `SORT`) and 19 call sites of `getAllBills()`, 26 of `getAllProducts()` / `getAllClients()` | Cost grows with every invoice; this is the real scaling wall |
| C6 | Sign-in is a **sequential waterfall**: `/v1/me` → `/v1/onboarding` → `/v1/workspace/local-prefs` → then the app draws, then lazy chunks, then the shell calls above | `features/auth/AuthGate.jsx:33-40` | 3 round trips before first paint; repeated after each onboarding step |
| C7 | Each auth phase (login, plans, setup, guide, app) is a full-screen swap that remounts and re-runs `refresh()` | `AuthGate.jsx` | Every "Next" in onboarding re-asks the server who you are |
| C8 | `preloadViews()` fetches every screen's JavaScript at idle | `App.jsx:84,158` | Dozens of chunk requests competing with data calls |
| C9 | The first JavaScript bundle is **902 KB** (plus 577 KB PDF and 217 KB React, lazy) | `dist/assets/index-*.js` | Slow first load on a phone |
| C10 | Backend per request: a transaction, row-level-security settings and an audit hook (not profiled on Railway) | `apps/api/src/http.ts` | Adds a fixed cost to every one of the 40 calls |

Not a cause: the server itself. `/health` answers in 1 ms and a failed sign-in in 46 ms locally. Hosting (region of the app and of the database) is the main unknown on Railway: if they are far apart, each of the 40 calls pays that distance.

### 3.3 The fix, with the expected result

| Step | Change | Result |
|---|---|---|
| S1 | **Server search.** Add `GET /v1/search?q=` (bills, parties, items, limit 8 each); the palette calls it as you type. Delete the corpus effect in `App.jsx` | −3 full-collection calls on every load |
| S2 | **Server notification summary.** Add `GET /v1/notifications/summary` returning counts and the first few rows (overdue, due soon, low stock, filings), computed in SQL; `useNotifications` calls it once and refreshes every few minutes | −2 full-collection calls on every load |
| S3 | **`useBusinesses()` hook** on TanStack Query (`staleTime` 5 min) replacing the 18 `listBusinesses()` effects | 7 calls → 1 |
| S4 | **`GET /v1/bootstrap`** returning `me`, onboarding state, preferences, settings, businesses and the profile in one transaction; `AuthGate` makes this one call | Sign-in waterfall (3 round trips) → 1; shell calls 8 → 1 |
| S5 | **Move `lib/data/*` onto TanStack Query** (`useQuery` with keys per collection and business), invalidated on save | Shared cache across screens; no repeated list loads |
| S6 | **Real list endpoints**: `GET /v1/invoices?cursor&limit&status&q&from&to` and the same for parties and items, backed by indexed columns instead of JSON; screens page 50 at a time. (This is item X4 in `FEATURE_GAPS_2026-11.md`; the typed tables already exist.) | Pages stay fast at 50,000 invoices |
| S7 | **Stop eager `preloadViews()`**: prefetch only the likely next screen on hover or focus of its menu item | Fewer competing requests |
| S8 | **Bundle**: split `index` (902 KB) by route group, move `jspdf`/`html2canvas` behind a dynamic import (already a separate chunk, confirm nothing pulls it eagerly), enable gzip/brotli in the production server | First load less than 300 KB gzipped |
| S9 | **Deployment**: put the API and Postgres in the same Railway region; enable connection pooling; add `Server-Timing` headers and a per-endpoint latency log | Removes the distance cost; makes the next slowness diagnosable in minutes |
| S10 | **Guard rail**: a test that fails when a page makes more than 8 API calls (`audit-netprof.mjs` already counts them) | Stops this coming back |

**Acceptance:** a navigation makes at most 6 API calls; sign-in to a drawn Home needs one API call before first paint; `/reports` and `/accounting/*` make none of the stock, notification or search calls; the same holds with 5,000 invoices.

## 10. What is unique, and what to build to be unmistakable

**Already unique (say it on the front page):**

1. **"Files with zero portal rejections."** Every return is checked against the department's schema and its validation rules **by number** before it can be saved (123 ITR-3 rules, the ITR-4 rules, GST pre-checks), with a CA review and approval step and an acknowledgement record. No competitor in this price range does this.
2. **Books to income-tax return.** ITR-3 and ITR-4 files built from the ledger and the asset register, with advance tax, challans and an AIS/TIS match. Vyapar, Zoho, Tally, myBillBook and Busy stop at GST.
3. **A free CA seat and a practice dashboard.** The CA works on the client's data with the client's permission; no export, no e-mailing of Excel files.
4. **Compliance that warns before the notice.** Cash Watch (cash payments over ₹10,000 under 40A(3), cash receipts over ₹2 lakh under 269ST, MSME dues under 43B(h), ITC 180-day reversal) tells the owner while they can still fix it.
5. **Audit-grade honesty.** An append-only edit log that nobody can switch off, **Verify My Data** checks, period locks, and a rule that the return follows the ledger and says when the asset register disagrees.
6. **Row-level security and sealed identity data** (Aadhaar, bank numbers).
